# 模型、上下文与记忆

模型负责生成或决策；上下文决定模型本轮能看到什么；记忆决定哪些历史信息可以跨轮次保留。三者混在一起配置，往往会造成 Token 超限或旧信息污染。

## 记忆策略比较

| 策略 | 适合场景 | 优点 | 代价 |
| --- | --- | --- | --- |
| `none` | 单轮问答、无状态工具 | 最可控、成本低 | 不保留历史 |
| `full` | 短对话、调试 | 信息完整、实现直观 | 上下文线性增长 |
| `sliding_window` | 稳定的多轮助手 | 只保留最近若干轮 | 早期事实会被丢弃 |
| `summary` | 长对话、客服 | 压缩旧历史 | 摘要可能损失细节 |
| `buffer` | 需要按 Token 限制保留上下文 | 预算明确、行为可预测 | 需要根据模型窗口调整预算 |
| `hierarchical_file` | 跨会话工作流 | working/session/agent 分层 | 需要更严格的晋升和清理策略 |

配置中的 `window_size`、摘要触发轮数和 Token 预算，应结合模型上下文窗口与真实请求长度调整。平台把“一轮”定义为用户消息以及后续助手回复、工具调用和工具结果的完整链路，而不是一条消息。

## 选择模型的检查表

1. 先确认模型资源连通和模型标识正确。
2. 再验证上下文长度、结构化输出和工具调用能力。
3. 需要图片时确认 `supports_vision` 和供应商请求格式。
4. 记录温度、最大 Token、推理强度等参数，保证评测可复现。

## 典型故障

- 回答遗忘近期信息：检查窗口大小和上下文组装日志。
- 回答引用过期信息：检查长期记忆晋升与清理策略。
- 图片请求被当成文本：检查消息内容块、模型视觉能力和适配器。
