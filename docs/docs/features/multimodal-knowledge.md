# 多模态知识库设计

当前知识库产品页面的上传格式主要是 PDF、DOCX、DOC、TXT、MD；后端消息协议已兼容图片内容块，LLM 配置也保留 `supports_vision` 字段。因此，多模态是清晰的扩展方向，但不能把“消息可以携带图片”误写成“知识库已经完成图片向量化”。

如果只是让用户在一次对话中上传图片并交给视觉模型分析，请使用已实现的[智能体多模态输入](../agents/multimodal-input.md)链路。本页讨论的是长期知识资料的解析、索引与检索。

## 推荐扩展链路

```text
图片/PDF 页面
   ↓ 视觉 Reader：OCR、版面、图表和图片描述
统一 Document：文本 + image_ref + metadata
   ↓ 多模态 Embedding
Milvus 向量 + MongoDB 元数据
   ↓
视觉模型读取证据并生成答案
```

## 与纯文本知识库的差异

| 环节 | 纯文本 | 多模态 |
| --- | --- | --- |
| Reader | 文本抽取和分块 | OCR、版面解析、图片引用和表格识别 |
| Embedding | 文本向量 | 图文共享向量或分别建索引 |
| 存储 | 文本块和来源 | 文本、图片地址、页码、裁剪区域和权限 |
| Prompt | 注入文本证据 | 同时注入文本和视觉内容块 |
| 评测 | 语义召回、引用 | 图表理解、区域定位、跨模态召回 |

## 安全与可追溯

图片引用必须有权限和生命周期；不要把临时下载地址写入长期记忆。检索结果应保留来源文档、页码或区域信息，答案才能回溯到原始证据。

## 落地顺序

先扩展 Reader 和统一 Document Schema，再验证 Embedding 维度与 Milvus Collection 一致，最后接入支持视觉输入的模型。任一环节缺失，都只能算“图片消息演示”，不能算可运营的多模态知识库。
