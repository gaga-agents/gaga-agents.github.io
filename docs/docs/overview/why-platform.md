# 为什么需要智能体平台

模型调用解决的是“生成下一段内容”，真实任务要求的是“在约束条件下持续完成目标”。二者之间存在状态、工具、数据、控制流和运维治理等工程差距。

## 从模型调用到任务执行

一个单次模型调用通常只有输入、模型和输出。一个智能体任务则可能需要：

- 在多轮交互中保留必要状态，同时控制上下文长度；
- 根据目标选择规划策略，分解任务并处理失败重试；
- 检索企业知识，并区分证据、推断和模型固有知识；
- 调用外部工具、代码或机理模型，并约束权限与资源；
- 输出可检查的执行轨迹，支持调试、评估、发布和回滚。

因此，平台的价值不是把所有能力塞进一个页面，而是建立一条可重复、可验证、可治理的交付链路。

## 五个工程域

### 状态管理

管理用户、项目、智能体和会话四层边界，在上下文、记忆与工作空间之间传递必要信息，避免不同任务互相污染。

### 任务编排

单智能体内部可使用 ReAct、Chain of Thought、Plan-and-Execute 等策略；跨智能体任务由 DAG、条件、并行、循环和子流程表达。

### 知识增强

文档进入平台后要经过解析、切分、向量化、索引和可选的实体关系处理。运行时再根据问题完成召回、重排和证据注入。

### 工具执行

平台对 Skills、API、代码和机理模型提供统一的发现、参数校验、调用代理、超时控制与执行记录，必要时交给隔离沙箱。

### 长期治理

平台记录执行轨迹、日志、Token/成本、错误与服务健康，使团队可以定位问题、优化资源或 Prompt，并重新发布可追踪的版本。

## 平台边界

gagaduck-agents-platform 负责智能体工程基础设施和交付流程，但不会替代以下工作：

- 业务方对目标、权限和风险边界的定义；
- 数据所有者对知识来源、更新周期和合规性的负责；
- 模型提供方的可用性、价格与内容策略；
- 生产环境中的容量规划、密钥管理、网络安全和灾备制度。

清楚这些边界，才能把平台当作工程底座，而不是一个“自动解决所有问题”的黑盒。
