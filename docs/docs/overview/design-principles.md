# 平台设计亮点

平台的优势不只是“页面上能配置智能体”，而是把一次运行拆成可以观测、恢复和审计的工程对象。下面的设计均对应当前后端实现，而不是抽象口号。

## 1. Turn / Step / Execution 三层运行台账

`AgenticLoop` 以 turn 驱动用户一轮请求，以 step 驱动每次模型或工具推进，以 execution 记录完整运行。每个事件都会补充 `execution_id`、`turn_id`、`step_id` 和 `segment_id`，因此前端可以把流式事件、消息、工具调用和最终结果准确关联。

```text
Execution
 ├─ Turn 1: 用户问题
 │   ├─ Step 1: LLM 决策
 │   ├─ Step 2: Tool / Knowledge
 │   └─ Step 3: 最终回答
 └─ ExecutionReport: tokens / iterations / steps / errors
```

## 2. 策略与执行器解耦

策略只提出 `StepPlan` 和 `StepRequest`，具体模型、工具和消息推进由 `StepDispatcher` 及运行时执行。这样 ReAct、计划执行和自定义策略可以共享状态、事件、重试和持久化边界，新增策略不会复制整套执行循环。

## 3. 上下文预算是组合预算

`ContextAssembler` 为 Prompt、工具描述、Few-shot、运行时状态、外部 Skill 和单条消息分别设置预算，并统一组装。工具库选择器还会根据任务先筛选工具，遇到文件任务自动补充文件能力，避免把全部工具无差别塞给模型。

## 4. 控制命令可在 step 边界生效

取消、暂停、恢复和用户插话不是直接杀掉一个进程。运行循环在 step 边界轮询持久化命令，插话进入 Inbox，未消费的输入会被释放回队列；这样控制行为有明确顺序，也能在后台任务和流式连接之间保持一致。

## 5. 高风险工具有显式确认状态

工具执行可以进入 `pending_confirmation`，等待用户批准或拒绝；确认记录以 Mongo 条件更新协调，支持超时、取消、冲突决策和幂等提交。安全控制因此成为执行状态的一部分，而不是前端弹窗的“装饰”。

## 6. 失败恢复优先于重新运行

编排运行状态包含 `waiting`、`paused`、`resuming`、`cancel_requested` 等中间状态，终态明确区分 `success`、`failed`、`cancelled`。恢复时应从执行状态和已持久化的节点结果继续，而不是无条件重放全部副作用。

## 与普通脚本式 Agent 的差异

| 维度 | 普通脚本 | gagaduck-agents-platform |
| --- | --- | --- |
| 调试 | 只能打印最终结果 | 事件、步骤、工具、Token 和状态台账 |
| 扩展 | 每种策略复制循环 | 策略、Dispatcher、运行时分层 |
| 上下文 | 字符串不断追加 | 分项预算、截断和工作空间索引 |
| 控制 | 杀进程或重新提交 | step 边界取消、暂停、插话和恢复 |
| 安全 | 由调用方自行判断 | 工具确认、超时、冲突和审计记录 |
