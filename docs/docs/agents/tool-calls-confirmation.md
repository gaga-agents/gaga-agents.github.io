# 工具调用与安全确认

工具调用让智能体从“生成文本”扩展为“读取文件、查询知识、访问 MCP 或执行机理模型”。平台把工具发现、模型决策、人工确认、实际执行和结果观察拆成独立阶段，避免模型生成一个调用后立即产生不可控副作用。

## 执行链路

```text
加载可用工具
  ↓ 生成 name / description / parameters Schema
模型决定是否调用并生成 arguments
  ↓
解析 tool_call 并分配 tool_call_id
  ↓ manual 模式进入 pending_confirmation
实际执行：Builtin / KB / Skill / MCP / Scheduler
  ↓
生成 ToolCallComplete 或 ToolCallError
  ↓
工具结果作为 observation 返回模型
  ↓
模型继续调用工具或生成最终回答
```

工具调用是否出现，既取决于工具配置，也取决于所选模型是否支持或能够稳定生成平台要求的工具调用结构。

## 三种工具模式

`tool_config.mode` 支持：

| 模式 | 行为 | 适合场景 |
| --- | --- | --- |
| `none` | 不加载任何工具定义，智能体只能直接回答 | 纯问答、验证 Prompt、禁止副作用 |
| `auto` | 模型自行决定是否调用，调用后直接执行 | 低风险、可重试、权限已收敛的工具 |
| `manual` | 模型仍自行选择工具，但每次实际执行前等待用户确认 | 写入、删除、外部请求、费用或其他高风险操作 |

`manual` 不是“用户替模型选择工具”，而是“模型提出调用，用户批准副作用”。内置工具、知识库工具、外部 Skill、MCP 和外部机理模型都会经过同一个确认边界。

关闭工具模式后，工具库、Skill 和 MCP 配置仍可保存在智能体中，但运行时不会加载；上下文会明确提示当前没有可用工具。

## 工具从哪里来

智能体运行时可以组合以下来源：

- 单独配置的工具；
- 工具库中的工具；
- 内置文件和 Web Search 工具；
- VectorRAG / GraphRAG 知识库工具；
- 外部 Skill 的脚本执行工具；
- MCP Server 动态发现的远端工具。

运行时把各来源归一化为 function 定义和执行映射。MCP 工具会生成稳定的本地别名，避免不同 Server 的同名工具冲突；真正调用时仍使用远端原始工具名称。

## 模型如何选择工具

模型看到的每个工具至少包含：

```json
{
  "name": "search_documents",
  "description": "按关键词搜索项目文档",
  "parameters": {
    "type": "object",
    "properties": {
      "query": {"type": "string", "description": "搜索关键词"},
      "limit": {"type": "integer", "default": 5}
    },
    "required": ["query"]
  }
}
```

工具名称决定模型输出的调用目标，描述影响“什么时候用”，Schema 和示例影响“怎么填参数”。描述应说明适用场景和限制，不要只重复工具名称。

为避免把过多工具全部放入上下文，平台会先选择相关能力源：

- 工具总数不超过 25 时，通常直接加载全部已启用工具；
- 工具较多且来自多个工具库时，可以根据用户输入筛选相关工具库；
- 配置 MCP Server 时也会启用动态能力源选择；
- 文件任务会结合内置文件能力和工具元数据参与选择。

能力源选择减少上下文噪声，但也可能把需要的工具筛掉。排查“模型看不到工具”时，应先确认该工具是否进入本轮工具定义，而不只是检查智能体配置页是否勾选。

## 参数 Schema 的作用

Schema 为模型和执行器提供字段约束：

- `properties` 定义字段名；
- `type` 定义字符串、数字、数组或对象；
- `required` 表示必填字段；
- `enum` 限定可选值；
- `default` 提供默认提示；
- `format: binary`、`contentMediaType` 或 `x-type: file` 标记文件参数。

工具存在 `example_input` 时，平台会把示例作为强提示放入工具说明；缺少参数 Schema 时，也可以从示例推断基本类型。示例只能辅助生成，不能替代正式 Schema。

:::warning Schema 不是唯一的安全边界

模型仍可能生成缺字段、错误类型或无效业务值。不同执行目标的校验能力也不同，因此工具实现必须再次验证输入、权限、资源归属和业务约束，不能只相信模型参数符合 Schema。
:::

## 人工确认状态机

`manual` 模式下，每个调用创建一条持久化确认记录：

```text
pending
  ├─ 用户同意 → approved → applied → 执行工具
  ├─ 用户拒绝 → rejected → 跳过工具
  ├─ 300 秒无决策 → expired
  └─ 执行被取消 → cancelled
```

确认记录保存 `confirmation_id`、`execution_id`、`session_id`、`turn_id`、`step_id`、`tool_call_id` 和 `user_id`，用于校验归属和跨实例协调。工具名称与参数通过 `tool_call_pending_confirmation` SSE 事件发送给前端。

具体过程为：

1. Runtime 创建 `pending` 记录并发出等待确认事件；
2. 调试页展示工具名称、参数以及同意/拒绝按钮；
3. 用户使用事件中的 `confirmation_id` 提交决策；
4. 执行实例轮询 MongoDB 并原子领取决策；
5. 同意后才发出 `tool_call_start` 并执行工具；拒绝、超时或取消都不会执行工具。

默认确认超时为 300 秒。等待确认期间，该 Turn 尚未完成，后续普通消息仍进入 Session 队列。

## 同意、拒绝、超时与重复提交

| 情况 | 结果 |
| --- | --- |
| 同意 | 状态收敛为批准并由当前执行领取，然后执行工具 |
| 拒绝 | 发出拒绝事件，写入“工具被拒绝”的 Tool Message，模型可基于已有信息继续 |
| 超时 | 状态变为 `expired`，发出工具错误，调用被取消 |
| 执行取消 | 等待记录变为 `cancelled`，不再接受决策 |
| 重复提交相同决策 | 幂等返回已有结果 |
| 重复提交相反决策 | 返回 `409 Conflict` |
| 记录不存在、过期或不属于当前用户 | 返回 `404` |

前端应以服务端响应和后续 SSE 为准。按钮点击成功只表示决策已保存；真正的工具开始由执行实例领取决策后触发。

## 工具失败、重试与继续执行

工具执行使用 `execution_config.max_retries`，总尝试次数为：

```text
1 次初始执行 + max_retries 次重试
```

MCP 返回 `is_error`、Scheduler 执行失败、文件不存在、执行目标缺失或其他异常都会进入重试。达到上限后，运行时：

1. 写入失败的 `ToolCallRecord`；
2. 发出 `tool_call_error`；
3. 把结构化失败说明作为 Tool Message/Observation 返回策略；
4. 由当前策略决定改参数、换工具、继续回答或结束。

因此，普通工具错误不一定立即终止整个 Turn。即使 `error_handling=stop`，工具执行器也会先把可观察的失败交回 AgenticLoop；不要把它理解成“第一个 `tool_call_error` 必然停止”。

全局 `error_handling` 还支持 `continue` 和 `fallback`。其中 `fallback` 会在循环自然完成前发生未处理异常时返回配置的 `fallback_response`。是否能继续还取决于策略、总超时、最大 Step 和最大工具迭代次数。

运行时会检查最近 8 条工具记录，拦截同名、同参数的重复调用：最近成功时复用已有观察，最近失败时返回重复失败提示，避免模型陷入原样重试循环。

## 文件参数如何传给工具

机理模型工具的文件参数应使用当前 Session 工作区中的相对路径，例如：

```json
{
  "input_file": "reports/input.csv"
}
```

当 Schema 使用 `format: binary`、`contentMediaType` 或 `x-type: file` 时，工具说明会提示模型填写工作区相对路径。运行时也会结合参数名和扩展名识别常见文件参数。

执行前会：

1. 将路径限制在当前工作区；
2. 查找对应文件，包括上传后追加唯一后缀的文件名；
3. 读取文件并上传到 Scheduler 临时文件存储；
4. 把参数替换为包含 `_file_id`、文件名、大小和 SHA-256 的引用；
5. 由 Scheduler 将临时文件交给执行器。

不要让模型伪造 `_file_id`，也不要在 Prompt 中拼接绝对路径。文件不存在时，错误会列出可用工作区文件，模型应先调用文件列表或信息工具再重试。

上述自动上传主要用于通过 Scheduler 执行的机理模型。内置工具直接访问当前工作区；MCP 和外部 API 是否支持文件，取决于各自的参数协议，不能假设它们自动获得本地文件内容。

## 工具调用审计

一次工具调用可以从三类记录关联：

| 记录 | 主要内容 |
| --- | --- |
| SSE 事件 | pending、start、complete、error、rejected 等实时状态 |
| Execution 记录 | 工具 ID/名称、参数、结果、状态、错误、开始/完成时间和耗时 |
| Tool Message | 提供给模型的成功摘要、失败观察、拒绝或超时说明 |

关联坐标包括 `session_id`、`execution_id`、`turn_id`、`step_id` 和 `tool_call_id`。人工确认还应记录 `confirmation_id`、决策用户、决策状态和时间。

审计日志不应保存密码、API Key、Authorization Header、完整 Base64 文件或不必要的敏感工具结果。对写入、删除、付费或外部通知类工具，还应在业务系统记录操作对象、授权主体和幂等键。

## 推荐配置

| 风险 | 推荐模式 | 额外控制 |
| --- | --- | --- |
| 只读查询、知识检索 | `auto` | 项目权限、超时、结果大小限制 |
| 工作区读写 | `manual` 起步 | 路径隔离、文件类型和大小限制 |
| 删除、发布、付费、外部通知 | `manual` | 业务二次校验、幂等、详细审计 |
| 不允许任何外部动作 | `none` | 同时禁用不必要的知识和文件能力 |

上线前至少测试：合法参数、缺少必填字段、错误类型、无权限资源、确认同意、确认拒绝、确认超时、重复提交、工具超时、重试耗尽、重复调用和文件不存在。

## 常见问题

### 配置了工具，但模型没有调用

确认工具模式不是 `none`、工具已启用、工具库或 MCP 加载成功，并检查动态能力源选择是否把它纳入本轮。随后改进工具描述，让模型知道何时使用。

### 模型总是传错参数

检查 Schema 的字段名、类型、`required`、`enum` 和示例是否一致。不要在描述和 Schema 中使用不同名称；文件字段应明确标记为文件类型。

### 点击同意后一直没有执行

决策可能已保存但执行实例尚未领取，或 Session SSE 已断开。使用 `confirmation_id`、`execution_id` 和 `tool_call_id` 检查确认记录及后续事件。

### 工具失败后智能体仍然继续回答

这是当前可观察失败语义：错误先成为 Tool Observation，策略可以选择降级回答或换工具。检查最终答案是否明确说明失败，不要只看执行是否继续。

### 同一个工具不再重复执行

运行时会拦截最近的同名同参调用。要真正重试，应修正参数、文件路径或执行条件，而不是原样调用。
