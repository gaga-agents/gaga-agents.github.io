# 方案比较与选型

平台提供多种实现路径。选型时优先考虑可观测性、依赖复杂度和失败恢复，而不是只比较功能数量。

## 部署方式

| 方式 | 优点 | 代价 | 建议 |
| --- | --- | --- | --- |
| 单服务 Python 本地启动 | 启动快、便于断点和 Swagger 调试 | 不能代表完整 Gateway 路由和基础设施 | 开发单个微服务 |
| 多服务本地联调 | 反馈快、便于验证服务契约 | 依赖多，端口和环境变量管理复杂 | 后端接口联调 |
| Kubernetes V2 | 服务发现、存储和运行环境更接近交付形态 | 需要镜像、PVC、Nacos 和基础设施 | 集成测试和部署 |

## 智能体形态

| 方式 | 适合 | 主要风险 |
| --- | --- | --- |
| 单智能体 + 工具 | 责任清晰、流程短 | 工具过多会降低选择稳定性 |
| 计划与执行 | 多步骤且需要先拆解目标 | 计划过时或执行偏离 |
| 多智能体编排 | 专业角色、并行任务、独立评测 | 交接、Join、重试和成本复杂 |

## 结论

先用单智能体建立可回归基线，再引入工具、知识和编排。先用本地服务验证契约，再用 Kubernetes 验证交付拓扑。每一次升级都应保留前一版本的运行证据。
